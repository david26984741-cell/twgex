# 選擇權曝險地圖 — 台指 TXO / SPY / QQQ

由公開的每日盤後資料，算出全市場的 gamma / vanna 曝險結構，畫成五個面板：
逐履約價 GEX、逐履約價 VEX、GEX vs GEX+ 情境曲線、曝險摘要、到期日結構拆解。
三個標的共用同一套引擎與版面，上方分頁切換。

```
GEX  = M × S² × 0.01 × Σ sign × gamma × OI      元 / 標的移動 1%
VEX  = −M × S ÷ 100  × Σ sign × vanna × OI      元 / 隱含波動率 1 個百分點
GEX+ = GEX + β × VEX
```

純標準庫（Python 3.9+），前端無外部相依，可直接掛 GitHub Pages。

> **先讀這一段。** 「造市商曝險」是**假設**不是觀測——期交所公布的是全市場未平倉，
> 沒有任何欄位能識別造市商的方向。詳見 [METHODOLOGY.md 第 1 節](METHODOLOGY.md)。

## 自動更新

`.github/workflows/daily.yml` 的排程（時間都是台北時間，cron 寫死 UTC，所以全年固定）：

| 台北時間 | 標的 | 備註 |
|---|---|---|
| 週二～六 12:30 | SPX / SPY / QQQ | 抓的是**前一個**美股收盤。未平倉向 OCC 拿、價格取 CBOE，用哪一欄由 parity 自己挑 |
| 週一～五 15:15 | TXO ＋ SPX / SPY / QQQ | 台指一般時段 13:45 收盤、期交所盤後檔約 15:00 上架；順便當美股那班的補跑 |

兩班都會跑全部四檔，不依「哪一班」分流——分流栽過一次（2026/08/27 那輪 cron 明明是美股那班
卻掉進台指分支，美股整晚沒更新）。多跑一次永遠是安全的：`build.py` 抓到比現有舊的日期
只寫歷史檔、不動 `latest.json`，提交那步沒有變動就跳過。下午那班天然變成早上那班的補跑。
每個標的失敗會自動重試三次、每次隔 5 分鐘，涵蓋期交所或 OCC 晚上架的情況。

**美股那班為什麼排在台北 12:30。** 這裡有三層，每一層都踩過坑：

CBOE 那份 `delayed_quotes` 檔裡，價格是即時的、未平倉量卻是**隔天早上**才更新
（實測美東 10:00~10:30）。所以開盤前抓 → 價格對但未平倉舊一天；等未平倉更新 → 未平倉對了
但價格變成盤中。**沒有任何一個時點兩者同時正確。** 第一層解法是價格改取收盤價而不是盤中中價，
於是只剩「未平倉已更新」一個條件。

第二層是換掉未平倉來源。**OCC 自己就有逐履約價未平倉，而且早 CBOE 十幾個小時**
（`marketdata.theocc.com/series-search`，交易日當天美東約 20:00 ＝ 台北 08:00 就發布，
跨週末差 2.5 天），GitHub Actions 連得到。

**第三層是「收盤價」到底要讀哪一欄——2026/09/02 就是栽在這裡。**
檔案裡**標的**的 `prev_day_close` 在場次一結束就滾成當天收盤，但**每一檔選擇權自己的**
`prev_day_close` 要等美東隔天早上才滾，而且各標的、各序列滾的時間還不一樣
（2026/09/04 07:10 UTC 實測：SPX 與 QQQ 已經滾了、SPY 還沒）。原本的對齊檢查看的是標的，
標的確實滾了，所以檢查形同虛設，做出來的是「今天的現貨 ＋ 今天的未平倉 ＋ 昨天的選擇權報價」。
SPY 那天的總 GEX 因此多算了 62%（−9,238 vs 正確量級 −5,702 百萬美元）。

判準：**put-call parity 反解出來的遠期價只由選擇權報價決定**，跟標的報價完全獨立，
拿它跟現貨對照就查得出報價是哪一個場次的。`build.py` 每次都把
`prev_day_close` 與買賣中價各算一次遠期，挑貼現貨的那個用（`cboe.pick_price_field`）：

- 美東收盤後那段（正是這班抓的時候）→ **買賣中價才是剛收完場次的收盤報價**，選中價
- 隔天早上 CBOE 換日後 → `prev_day_close` 正確、中價變成盤前雜訊，選 `prev_close`
- 兩個都偏離現貨超過 0.35% → **整天不產出**，等下一班

門檻只是安全網，真正的判斷是「兩個都算、挑近的」——因為正常日的偏差
（QQQ 2026/08/27 是 −0.20%）跟出事那天（QQQ −0.23%）會擦邊，單看門檻擋不住。
每份 `latest.json` 的 `meta.fwd_check` 都記著當天用了哪一欄、遠期差多少。

時間點則由**晚的那個來源**決定：OCC 台北 08:00 就有，但 CBOE 收盤後那份報價檔實測
timestamp 是 03:57 UTC（＝台北 11:57）才換，所以排 12:30。比舊的台北 23:00 早十個半小時。
GitHub 排程延遲一到三小時都還在安全窗口裡，下午 15:15 那班再補一次。

`build.py` 會擋下 `oi_as_of != price_as_of`，等不到就整天不產出，不會畫拼裝圖。
產出的 `meta` 裡 `oi_as_of`、`price_as_of` 必須相同，`oi_source` 會標明是 OCC 還是 CBOE。
`--oi-source cboe` 保留成備援路徑（那條路才需要 `wait_oi.py` 等未平倉更新）。

**2026/09/23 Cboe CDN 停更，暴露了對齊檢查的漏洞。** 那天 03:56 UTC 起，
`cdn.cboe.com` 的延遲報價檔（SPX／SPY／QQQ，連 VIX、AAPL 都一樣）整個停更，停在 9/22 收盤。
9/24 那四班照樣「成功」：9/22 的報價配上 OCC 已經是 9/23 的未平倉，標成 9/22，
把前一晚那份正確的 9/22 蓋成拼裝圖。漏洞在 **OCC 的日期是推的**——「CBOE 檔的未平倉日＋1 個交易日」，
前提是 CBOE 只落後一個發布週期；CBOE 停更超過一天，前提就失效。
而原本拿來確認 OCC 發布了沒的 `daily-open-interest`，`reportDate` 其實只決定**月份**、回的是整個月的月報，
所以舊的探針永遠說「已發布」，從來沒擋過任何一次。現在兩道防線：

- **照日曆判定 Cboe 報價過期**（`cboe.quote_stale`）：日曆上最近一個已收盤的交易日（`us_last_session`）
  比檔案裡的場次還新，就是來源停更，不產出。不連網，靠 `calendar_us.txt`。
- **直接問 OCC 的日期**（`occ.latest_published`）：讀月報的日期欄，最大的那天就是 OCC 最新發布的交易日；
  不看假日檔，日曆寫錯也量得對。比價格舊＝OCC 還沒發布；比價格新＝報價停更。

`build.py` 的結束碼：0 成功；1 一般失敗（例如 OCC 還沒發布，重試可能有用）；2 參數錯誤；
3 來源停更（報價照日曆過期、或 OCC 已經比報價新，重試沒有用）。daily.yml 遇到**結束碼 3 不重試**，
其他照舊三次、每次隔 5 分鐘。任一標的這一班沒更新，資料照常提交（其他標的不受影響），
最後一步讓這一班**變紅**、GitHub 寄信；原因寫在該次執行頁面的 Summary（每檔一行中文）。
離線重跑舊的 `--json` 檔要加 `--date`，否則會被當天的日曆判成過期。

**報價的備援：Cboe 報價頁。** CDN 檔停更那段期間，Cboe 自己的報價頁
`https://www.cboe.com/delayed_quotes/{spx,spy,qqq}/quote_table` 照常更新，而且 HTML 裡內嵌的就是同一份資料
（`CTX.contextOptionsData`，欄位跟 CDN 檔相同，只是 timestamp 只有時分秒）。`build.py --quote-source auto`
（預設）平常照舊抓 CDN 檔；CDN 檔照日曆判定過期、或連不上／看不懂時，才改抓報價頁，每班每標的**至多 1 次**，
CDN 一恢復下一班就自動回原路。產出的 `meta.quote_source` 記著這次用的是 `cdn`、`page` 還是離線的 `file`。
報價頁一次約 16 MB（大半是頁面自帶的代號清單），所以不拿它當主要來源。兩邊都停在舊日期 → 結束碼 3；
報價頁連不上 → 結束碼 1（下一班再試）；頁面改版、找不到內嵌資料 → 結束碼 3（要改程式）。
條款與使用者同意見研究區 `ARCHITECTURE.md` 第 4 節 (f) 的例外款（2026-09-25）。

沒有保險班。期交所當天延遲上架的話，到 Actions 頁面按 **Run workflow** 補跑即可
（輸入框留空 = 三個標的都跑，只想補台指就打 `TXO`）。
手動與排程之間有 `concurrency` 群組擋著，不會同時跑，只會排隊。

資料沒更新（假日、來源延遲）時不會產生空提交。提交訊息會帶上各標的實際的資料日期，
例如 `曝險地圖更新 TXO 2026/08/21 / SPY 2026/08/21 / QQQ 2026/08/20`，
從 commit 清單一眼就看得出這次有沒有抓到新的一天。

## ES 分頁：由 SPX 換算，不是自己的資料來源（2026/09/21 起）

CME 封了 IP、公司也沒有 CME 的行情授權，所以那條線整個退役。ES 分頁改成
**把 SPX 的曝險結構換算到 ES（小S&P 期貨）的價格刻度**。

**為什麼換算得出來，而且完全不碰 CME。** ES 選擇權的標的是「最近到期的季月 ES 期貨」，
而期貨價格就是遠期價格；遠期價格我們本來就在算——`build.py` 對每個到期日都用
put-call parity 從 SPX 選擇權自己反解出遠期，那是只由選擇權報價決定的東西。
取「對到 ES 季月到期日」的那個遠期，就等於拿到了 ES 的期貨價格：

```
ratio = F(季月) / S(現貨)          ES 價位 ≈ SPX 價位 × ratio
```

**為什麼是乘不是加。** 基差 ≈ S×(r−q)×T 隨價位等比例變化。用加的在離價平 8% 的履約價上
會差五點；用乘的則 **K/F 完全不變**，IV、gamma、skew、flip 全部自動一致，
不必重算任何希臘字母（selftest 有驗：最大相對偏差 1.5e-6，純粹是四捨五入）。

**找季月要用 `code` 不能用 `ltd`。** SPX 的 AM 結算在我們的資料裡 ltd 已經往前挪了一個
交易日，用 ltd 會找不到或找到隔壁那檔 PM 的。ES 期貨的最後結算也是第三個星期五的 SOQ，
跟 SPX 的 AM 是同一個東西，所以優先取 `A` 那一檔。

**拿真的 CME 結算價驗過（2026/08/21~09/16，14 個交易日）：**

| | 天數 | 平均差 | 標準差 | 最大 |
|---|---|---|---|---|
| 離季月 7 天以上 | 11 | **−0.08 點** | 6.3 | 12 點 |
| 換倉週（剩 4／3／2 天）| 3 | — | — | −10／−73／−88 點 |

正常期沒有系統性偏差，殘差就是 SPX 選擇權買賣價差的寬度（0.16%）。
換倉週那三天**不是算錯，是指到不同的契約**——我們算 9 月，市場的未平倉已經滾到 12 月。
CME 公告的換倉慣例是到期前 8 天，但實測的交叉點落在剩 3 天，兩者對不起來，
而且只有兩天的樣本。**只有兩個樣本就挑一個門檻，就是「先假設再寫防線」**，所以不挑：
日曆規則照用（那是 CME 對「標的是哪一口」的定義），但在換倉窗口（14 天內）
把兩個季月都算出來，橫幅上兩個數字都給，讓看的人自己判斷。

**這張圖是什麼、不是什麼。** 是 **SPX 市場的結構畫在 ES 的刻度上**；
**不是** ES 自己那些選擇權的結構（ES 有自己的未平倉，履約價落在整數 ES 點位）。
金額仍是 SPX 部位的金額（乘數 ×$100），沒換成 ES 的 ×$50——換算金額會讓人以為
那是 ES 自己的曝險。頁面最上面的橫幅把這幾句話直接寫給使用者看。
拿 SPX 的結構看 ES 是有道理的：SPX＋SPXW 的未平倉是 ES 的四倍上下，
整個 S&P 複合體的 gamma 主要是那一池在推。

**換算放在前端（`app.js` 的 `deriveES`），不另外存檔。** 存一份等於把 SPX 的 53 MB
再複製一份進 repo（`data/` 本來就 140 MB），而且會有走樣的風險；前端算的話 SPX
那份已經在快取裡，切過去幾乎不用等。`es_view.py` 是同一套邏輯的 Python 版，
`selftest.py` 會用 node 跑 `tools/xcheck_es.js` 把兩份**逐值對照**，防止哪天只改了一邊。

分頁與來源的對應由 `data/symbols.json` 的 `derived_from` 決定，不寫死在前端。

**看門狗 `.github/workflows/watchdog.yml`（台北每天早上 08:00，週一~週五）。**
它跑在 GitHub 自己的機器上（`ubuntu-latest`），只讀 checkout 下來的 `data/*/latest.json`
與本 repo 的 Actions API——不連任何外部行情來源、不需要瀏覽器。失敗時 GitHub 會寄信。

三個**獨立**的訊號，任一個成立就讓執行失敗：

1. 資料日落後太多（**台指與美股三檔都是 >1 個交易日**）
2. 同一支 workflow **最近兩次排程觸發的執行連續沒成功**（手動 dispatch 不列入——
   那些多半是在試東西，列進來會誤報；`cancelled` 也算沒成功）
3. 有執行**排隊超過三小時還沒有 runner 來領**

**門檻為什麼是 >1 而不是 >2。** 2026/09 有兩次「剛好卡在門檻上」被放過：一次撞到美國
勞動節，一次漏掉的兩個場次中間隔著週末，落後都只算出 2。現在收緊成 >1，並且**故意比
網頁上那則紅字提醒嚴一格**：網頁是客戶隨時會打開的，寬一點是不要誤報紅字；這支固定在
台北 08:00 跑，那個時點該有的落後是算得出來的定值（週二~週五是 1、週一是 0），
所以 >1 不會誤報，而 2 一定是真的漏了一天。兩個反例都寫進 `selftest.py` 了。

**晚班：台北 21:30（週一~週五，2026/09/25 加）。** 同一支看門狗、同一套門檻，多跑一次。
21:30 時兩班美股（12:30、15:15，含常見的五小時延遲）都已經跑完，美股該有的落後是定值 1，

## 驗證過的東西

**內部不變量**（`python selftest.py`，19 項，2026/08/06~08/21 共 12 個交易日全數通過）：

- 買賣權 IV 一致性：同履約價價平 ±5% 內，買權 IV 與賣權 IV 中位差 0.13 個波動率點
- 遠期單調性、ATM IV 期限結構單調（20.6% → 28.3%）
- 零丟棄：OI 覆蓋率 100%，沒有任何 leg 因反解失敗被剔除
- Greeks 對 60 位精度數值微分：gamma / vega / vanna 相對誤差 ~1e-14
- 曲線 ↔ 長條圖一致（GEX 與 VEX 皆然）、到期別可加性、β=0 時 GEX+ ≡ GEX
- VEX 在價平兩側同號（vanna 的特徵，vega 版做不到）
- IV 反解往返：4,000 組隨機參數誤差 < 1e-5，零失敗
- 前端 ↔ 後端一致：網頁重組出來的總量與 Flip 跟 Python 完全相同

## 三個標的的口徑差異

| | 台指 TXO | SPY / QQQ |
|---|---|---|
| 資料源 | 期交所 optDataDown + 證交所加權指數 | CBOE 公開延遲報價端點 |
| 用的價格 | 結算價 | 買賣中價（bid/ask 的中點） |
| 契約乘數 | 50 元/點 | 100 股/口 |
| 顯示單位 | 億元 | 百萬美元 |
| 到期時間 T | 算到最後交易日之次一營業日（最終結算價在那天決定） | 算到最後交易日（PM 結算，收盤即到期） |
| 未平倉時間差 | 當日盤後即公布 | OCC 隔日早上才發布，所以排程放在美東開盤前抓前一日 |

CBOE 端點自帶的 `iv` 與 greeks 欄位大量為 0、不可信，本專案一律自己反解、自己算。
